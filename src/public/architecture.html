Architecture

How this thing is built, what runs where, and what I'd do differently with more time. Source: github.com/Karthikgkamath/gnani_assignment

Stack, in one line

Node.js + Express serving a plain HTML/vanilla-JS frontend, SQLite for data, audio files stored on disk, Gnani's STT APIs for transcription (plus ffmpeg for the chunking fallback below), Gemini for the summary. No frontend framework, no ORM — there just isn't enough surface area here to justify either.

Upload → transcript flow

  1. Browser uploads the file via XMLHttpRequest (so we get real upload-progress events) to POST /api/notes.
  2. The server saves the file to disk, inserts a row in SQLite with status = uploaded, and responds immediately with the note id. The browser is redirected to the note page, which starts polling.
  3. A background task picks the note up and transcribes it — see "Long-audio handling" below for exactly how, since that ended up being more interesting than planned.
  4. Status moves to transcribing → summarizing → done (or failed) as each stage completes. The transcript is saved to SQLite as soon as it's back, before the summary step even starts.
  5. Once we have a transcript, it's sent to Gemini with a short prompt asking for a paragraph + bullet takeaways. The result is saved and status flips to done.

File storage

Audio files are written straight to disk under a data directory (DATA_DIR/uploads), named by a random UUID so we never trust the original filename for anything but display. SQLite lives right next to it (DATA_DIR/notes.db). On Render both live on a mounted persistent disk, so they survive restarts and redeploys. This is deliberately not S3/Blob storage — for a single small instance, a disk is simpler and there's nothing an object store buys us yet.

Long-audio handling

Gnani has two STT endpoints, and this is the part of the build that didn't go as documented. The plain REST endpoint is synchronous and, per the docs, capped at 60 seconds ("ideal ≤30s"). The Batch endpoint is meant for everything longer: submit a job, start it, poll until done, fetch the transcript — a much better fit anyway, since the browser is never left holding an open connection for a multi-minute transcription.

In testing against the real API, every batch job came back START_FAILED with a server-side ReadTimeout — reproduced with five separate jobs, different file sizes, and even a raw curl request with no app code involved, so it's a backend/account issue on Gnani's side rather than a bug here. The sync endpoint, on the same key, worked instantly and accurately — but its real limit turned out to be a hard 30 seconds (MAX_AUDIO_DURATION_EXCEEDED above that), not the 60 documented.

So the app does both: it tries the batch flow first, exactly as documented, since that's the correct design and it'll start working the moment Gnani's batch pipeline does. If that fails, it automatically falls back to splitting the audio into ~25-second pieces with ffmpeg, transcribing each through the sync endpoint, and stitching the text back together in order. This is the path that's actually running right now, and it's what a 2+ minute note goes through today — verified end-to-end with a 108-second clip. The 10MB-per-file cap the batch endpoint documents is still enforced on upload either way, client-side and server-side.

What runs sync vs. background

  • Sync (inside the request): receiving the upload, validating file type/size, writing it to disk, creating the DB row.
  • Background (after the response is sent): the whole Gnani job lifecycle (create/start/poll/fetch), and the Gemini summarization call. Both can take anywhere from a few seconds to a few minutes, so they run in an in-process queue and the note's status column is the source of truth the frontend polls against.

The queue itself is intentionally the simplest thing that works: an in-memory array processed one job at a time in the same Node process that serves HTTP requests. It's not durable — a restart mid-job loses that job's progress (the note just sits in transcribing forever, which is a bug, not a feature). Fine for a demo on a single instance; not fine at real scale.

Failure handling

Every stage (upload validation, Gnani calls, Gemini call) is wrapped so a failure updates status = failed with a human-readable error_message instead of crashing the worker or leaving a note stuck silently. All outbound API calls have a timeout (AbortSignal.timeout) so a hung upstream request can't wedge the queue forever. Gnani calls that come back 429/500/503 — the docs call these out as transient — are retried up to 4 times with exponential backoff before the note is marked failed; this isn't theoretical, it's what actually happened testing against the real API (a burst of requests tripped a rate limit on the second call of a job). Anything else (bad request, auth failure, corrupt file) fails immediately since retrying won't help. The frontend shows all of this inline on the note page rather than a generic "something went wrong."

What I'd improve with more time

  • Swap the in-memory queue for something durable (BullMQ + Redis, or even just a jobs table with a recovery pass on boot) so a server restart doesn't strand in-flight notes.
  • Move audio storage to S3-compatible object storage once this needs to run on more than one instance — a local disk doesn't scale horizontally.
  • Auth — right now every uploaded note is visible to anyone with the URL. Fine for a demo, not fine for real use.
  • Webhook instead of polling — Gnani supports a callback_url on batch job creation, which would remove the poll loop entirely once batch is reliable.
  • Overlap the chunk boundaries in the sync-endpoint fallback (e.g. re-transcribe the last second of each chunk) so a word split exactly across a cut point isn't dropped or duplicated.
  • Once Gnani's batch pipeline is confirmed working again, drop the fallback's chunk count down or remove it — right now every note pays the cost of a failed batch attempt before falling back.
